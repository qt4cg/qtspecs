** PR #3065: 3064 ~fn:jvalue~: accept any item
:PROPERTIES:
:CUSTOM_ID: pr-3065
:ID:       73945E0B-34DB-41FD-A650-4CDCF8429CD4
:END:
See PR [[https://qt4cg.org/dashboard/#pr-3065][#3065]]

+ CG: This is about the ~jvalue~ function. When you use the ~data()~ function
  works on all input. But ~jvalue~ only works for JNodes. The idea is to make
  ~jvalue()~ just return the value unchanged if it isn’t a JNode
+ MK: I like the convergence with the ~data()~ function. I’m almost inclined to call it ~jdata()~ instead of ~jvalue()~
  + … The ~data()~ function is one of the few that maps over a sequence.
+ RD: On that note, given the similarity, is there a reason not just merge the functionality into ~data()~?
+ CG: The semantics are slightly different for coercion and mapping.
+ MK: If the JNode maps an array, the array doesn’t get atomized.
+ JWL: If ~jvalue()~ works over a sequence, do we have a problem where the
  ~jnode()~ value is a sequence, you’d get sequence concatentation in the
  result. Is that going to be a problem?
+ MK: If you give ~data()~ a sequence, it flattens it. You can be explicit if you want something else.
+ CG: We could have ~jvalue()~ as is and add a ~jdata()~ that takes arbitrary sequences.
+ MK: I don’t think it’s really needed.

Proposal: Accept this PR.

Accepted.

** PR #3081: 2935B Arithmetic Mode Decimal
:PROPERTIES:
:CUSTOM_ID: pr-3081
:ID:       78B3FEF6-4AF6-4F3F-92FC-7606AD03E9BB
:END:
See PR [[https://qt4cg.org/dashboard/#pr-3081][#3081]]

+ MK: This was requested by a user in a very detailed description motivated by
  the requirement in EU accounting standards to use decimal arithmetic.
+ MK: It changes a few functions and XQuery and XSLT to set options in the static context.
+ MK: Arithmetic mode decimal is added to the static context. 
+ MK: You can specify “decimal” or “double” which is what we do now.
+ MK: Coercion is sensitive to the arithmetic mode in the static context.
  + … The expression providing the value determines which static context that’s relevant.
  + … There’s a special case for ~xs:numeric~ in union types.
+ MK: In the section on arithmetic, we call out the preferred numeric type.
+ MK: ~declare option arithmetic-mode "decimal;"~ is added to the XQuery options.
+ MK: This is an optional feature; it’s not something that every user or every implementor might need.
+ MK: For XSLT, it’s just about setting options.
  + … There’s a new standard ~[xsl:]arithmetic-mode~ attribute.
  + … There’s a new system property that tells you what the arithmetic mode is.
+ MK: In Functions and Operators
  + … Many functions, like ~fn:avg()~, become context sensitive to the arithmetic type in the static context
  + … And it gets added to system properties
+ JWL: Part of the motivation was accountancy rounding modes. We had a whole table of half a dozen of those. 
+ MK: This one doesn’t tackle rounding. This is separable from rounding.
+ AP: Won’t this require some additional profiling to determine if I’ve done the right thing in all my static contexts?
  + … In spots, I’d need to insert some checks or something. Isn’t that an additional burden on the users?
+ MK: There’s some additional complexity, but if you need it it’s manageable.
+ CG: The original feature request proposed to return decimal for ~fn:number~,
  maybe it would be more consistent to go one step further and adjust some functions too.
  + … At least for me, it’s common that the ~data()~ and ~number()~ function do the same thing.
+ MK: I resisted that because ~number()~ is from 1.0 and you can use the
  ~xs:numeric~ constructor to cast to numeric. That will do the right thing because it’s casting to ~xs:numeric~.
  + … I didn’t think we needed to change number, but I’m not averse to it.
+ CG: My feedback is implementation driven; we have many cases in the code where
  if atomization will occur, we rewrite it to use the number function. From our
  perspective it would be more consistent to do it everywhere the same.
  + … Basically, I think it’s a nice step forward and I remember other cases where double was problematic.
+ MK: The other place I’ve deviated from the user’s proposal is INF and NAN. I’ve made that an error in those special cases.
+ JWL: AP’s point about debugging in situations where the static context can
  vary all over the shop, is there a case for a function that tells you (as a
  map) what the static context contains?
+ MK: We have a lot of little functions that do parts of that.
+ JWL: Yes, but what about the general case.

Some discussion of the complexity. Do you want to know all the statically declared variables?

+ RD: Having access to things like the declared variables and values would be useful for implementing debugging in IDEs.
+ MK:  Yes, but it’s also a nightmare for optimizers.

Proposal: Accept this PR.

Accepted. 

MK to sort out the base of the PR and then merge it.
