2.2. PR #3056: 3053 Guarded expressions: runtime type errors

See PR #3056

CG explains the PR. Testing revealed that some expressions needed to be guarded.

  • CG: The definition of a guarded has been updated to add a type error detected during dynamic evaluation.
  • MK: I think what worries me here slightly is just-in-time optimization.
    • … If we’re allowed to do something statically, should we be allowed to do it in a runtime JIT optimization?
    • … For example, once you know the values of global parameters, some optimizations are easier.
    • … This says if you delay the optimization, you can’t report it.
  • CG: Let’s keep it open and have another look.
  • MK: I do know that there are problems here; there are users who complain about type errors on a conditional branch when you can see clearly that it’ll never be executed.
  • RD: Am I right in think that a type error is a subset of a dynamic error?
  • MK: No, it’s a third category.
  • CG: It can happen during the static or dynamic phases.
  • RD: It would be useful to see some examples.
  • MK: It’s muddled in our case by the fact that we don’t make a completely clear distinction between static and dynamic phases anyway.
    • … We allow JIT compilation of template rules; we think of that as a delayed part of the static process.

  • RD: What this section is saying is that if the processor can guarantee that given the current static context and values of variables and things that a guarded expression won’t trigger therefore they can do optimizations

    • … Like for example in the (1 to $n) case they can short circuit.
    • JLO: This looks very similar to a bug that I found recently.

Revisit in the future.

2.3. PR #3073: 3072 Switch, typeswitch: optional default clause

See PR #3073

  • CG: It’s a bit more than editorial, but it should be easy to explain.
    • … The switch and typeswitch expressions require a default case.
    • … But we now have enums and choice item types where we know that the list is exhaustive.
    • … My proposal says that the default clause can be omitted and there’s a new error if the processor falls of the end of the list.
  • MK: A sensible thing. My only question is, XSLT defaults otherwise to returning an empty sequence rather than raising an error.
    • … I wonder what the relative merits are.
  • CG: An error gives you better control.
  • MK: In terms of handling semi-structured content where the typeswitch is over a collection of elements that’s over a collection of elements that might appear in the input…well, I suppose you can always have an explicit default clause that returns empty sequence.
    • … There are probably use cases for both.
    • … It just seems slightly odd to make them different.
  • CG: Yes, I can see that.
  • JWL: Is typeswitch in XPath?
  • RD: No, it’s only in XQuery.
  • JWL: Is there any reason not to put it in XPath?
  • MK: I don’t think there’s a strong justification anymore for not having it in XPath.
  • JWL: I’d suggest putting in in XPath.

Proposal: CG to rewrite for returning the empty sequence instead of error; mark as “merge without discussion” for next week.

2.5. PR #3076: 2935A: Default function options in the static context

See PR #3076

  • MK: This came about by a slightly devious route. In a very detailed issue about arithmetic modes and defaults. One item in that was the ability to change the default rounding mode globally to handle accounting standards.
    • … Thinking laterally from that, I wonder if we need a more general mechanism to set options from the static context.
    • … What I forgot when proposing that is that the rounding mode of round is not an options parameter, so that ended up being treated specially anyway!
  • MK: What the proposal does is add default options to the static context and I’ve defined syntax in XSLT for setting them.
    • … I haven’t designed syntax for XQuery, but I thought I’d get input first.

MK reviews the XSLT specification.

  • MK: The substance of it is in 5.6.
    • … There’s a xsl:default-function-options instruction to set default options for a particular function.
    • … It’s a bit difficult to define in XQuery because I’m exploiting static expressions in XSLT.
    • … There’s detail about when you have to check the options.
    • … It got too complicated to try to define them for dynamic function calls, only static ones.
    • … And there are a number of places where they don’t apply.
    • … They do apply when you pass options to a static function call.
  • RD: In XQuery, there’s a declare option syntax, the options declarations in the prolog. We could extend that.
  • MK: Yes, that’s probably what I’d do. But it’s a bit tricky because we don’t have static options.
  • JWL: In one sense, this is effectively a record but it’s one that gets put by default on the appropriate function calls.
    • … You could do that by defining a record for the function options.
  • MK: Sort of.
  • JWL: What happens for curried functions.
  • MK: At the moment, it only applies to static function calls, not partial applications. That’s to make things simpler.
  • JLO: I like this, I would like to see this in XQuery. We do already have that in part as we can do that in global configurations.
    • … The context can take a lot of defaults from there.

Some discussion of how the options are applied, in brief: they’re merged.

  • CG: I can see the advantages of having XQuery syntax. But I’m a bit hesitant because it’s powerful machinery but it can’t do everything. Lots of applications have dynamic options and we put them on a variable that is referenced.
  • JK: What impact does this have on user-written XSL function instructions? Can be exploited by a user?
  • MK: At the moment, options parameters are only defined for system functions. I guess vendor extension functions could use them. There’s no current way to do it for user defined functions to exploit it.
  • JK: I think the prose needs to be made more clear on that point.
  • MK: I think it’s worth persuing. I’ll revise it.

2.7. PR #3054: 3050 Clarifications regarding errors and type inferences

See PR #3054

  • MK: I wrote this partly because I found I was confused.
  • MK: There’s a bit of clarification on dynamic errors.
    • … Disjoint value spaces aren’t a sufficent condition to raise a type error (consider fn:error)

MK reviews a number of examples.

  • MK: There’s no change to the status quo, just new notes and examples.
  • RD: In the match example, is the reason you can avoid that call because it’s a built-in function.
  • MK: No, it’s because it has a declared type of xs:boolean, so the type will always be xs:boolean.
  • RD: The XQuery type system is more of a hint; I’m thinking of the case where a user-defined function is specified to return an xs:boolean but returns "hello".
    • … In that case it would be a dynamic error when evaluating the function.
  • MK: It might be a dynamically detected type error and if you avoid evaluating the function, you might miss it.
    • … I think that’s the status quo.
