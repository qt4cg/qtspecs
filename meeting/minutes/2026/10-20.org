** Issue #2914: Define a new char/codepoint type.
:PROPERTIES:
:CUSTOM_ID: issue-2914
:ID:       48687F8F-DC0A-42CA-9F56-403D3A8DCD66
:END:
See Issue [[https://github.com/qt4cg/qtspecs/issues/2914][#2914]]

+ RD: How should we resolve the issues that MK raised?
  + … I propose that we should define an ~xs:codepoint~ on top of non-negative integers.
  + … Then we could update F&O to use that.
+ RD: MK raised the issue that although XQuery and the Data Model define some
  types, those were done in agreement with the XML Schema WG
  + … The lexical space could change but I think that issue will arise no matter
    what because codepoints to string will raise an exception if the lexical space changes.
  + … That’s also true of the string type.
+ MK: The namespace issue is a pesky formality, but not one we can ignore.
  + … My main comment is that the cost is out of proportion to the benefit
  + … It’s not all that useful, and invites speculation about why there aren’t also data types for other semantic concepts.
  + … Adding a new datatype across all the specs and implementations is expensive and doesn’t seem justified here.
+ RD: One of the benefits is that it makes it clearer to a user reading the
  specs what the types are and what expected values they have. The current ~xs:integer~ isn’t ideal for code points.
+ JWL: Echo MK’s thoughts. If we start adding this, we have to make sure that we
  define operations (like comparisons and arithmetic). I expect it’s an enormous amount of work.
+ RD: I don’t think that’s an issue because I’ve proposed that it should be a
  restriction on non-negative integer, so all of the operations on numerics
  apply.
+ JWL: But for example, suppose you permit addition of an integer onto a codepoint, now you have to ask if the result is still a codepoint.
+ RD: We don’t specify the behavior of non-negative integer except for defining the lexical space.
+ CG: I think another implication is that we also have the notion of permitted
  characters; it could still be that we’d reject inputs that are codepoints if
  they’re not permitted characters.
+ NW: I don’t think we’re going to get consensus on this.

Proposal: Close this issue with no further action.

Accepted.

** PR #2881: 2873 fn:update: another attempt
:PROPERTIES:
:CUSTOM_ID: pr-2881
:ID:       D4A3FBA7-57B1-46E2-A563-CC02A8411FA4
:END:
See PR [[https://qt4cg.org/dashboard/#pr-2881][#2881]]

+ CG: We’ve had a look at this twice. I’ve made some minor revisions.
  + … We have one function ~fn:update~ that does a lot of things. But it isn’t a
    real replacement for the XQuery Update specification.
  + … You can do quite a lot with it as well.
+ CG: I’ve tried to rewrite the rules to make them easier to understand.

CG walks through the examples.

+ MK: Obviously, this is immensely powerful. My main concern is that there’s too
  much magic in how the value returned by the function determines what happens
  in the replacement.
  + … Instead of returning a simple value, return a record that includes an
    action plus a value.
  + … I think that would make it more explicit what kind of action you expect.
+ CG: One challenge here is to make it work for maps and arrays and XML.
  + … It’s not quite clear what “insert into” and “insert after” mean in each cases.
+ WP: Thanks for all of the hard work. The part that concerns me is, how much
  testing has this had in, for example, the XSLT context.
  + … What happens in the corner cases in XML for example.
  + … It seems that either this is pretty innocuous and I want it, or it’s dangerous and we should avoid it in XSLT.
  + … I’m concerned about the blurring of the boundaries. We need more use cases and demonstrations of the utility.
+ CG: Those are good points. I haven’t given a lot of thought to XSLT.
+ MK: One comment, I’ve been doing a lot of work on recursive descent
  transformation for arrays and maps. I’m not at all convinced that that
  approach can be optimized in the way this function could be optimized.
  + … This function might allow us to do in constant time what would other be linear.
+ RD: I think it will be useful for XQuery code because doing stuff that requires transforming data can be tricky.
+ NW: What should we do next?
+ CG: I feel like this one is pretty near done. 
+ MK: Maybe we should accept it and then work on improvements.
+ WP: I think that makes sense.

Proposal: accept this PR.

+ MK: With the expectation that I’d like to propose some changes…

Accepted.
