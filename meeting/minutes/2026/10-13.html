2.2. PR #2966: 2965 Regex functions: bugs

See PR #2966

  • CG: We discussed this before. I’ve incorporated MK’s comments. I think JK had comments on the new PR.
  • CG: Mostly what’s changed is a response to MK’s comment. I mostly adopted it as proposed.
  • MK: It was mainly to align the style of presentation for consistency with the rest of the spec.
  • JK: As I’m reading this, it looks like the two meta-characters match only zero-length segments.
  • MK: Yes.
  • JK: But I use them in cases where I think of segments as being longer than zero length. And outside of multi-line strings, I find the notion of segmentation difficult to understand.
  • MK: A segment is a tuple, a start position and a length. That’s a segment of the input string.
    • … This tells you if a particular meta character matches that segment.

Some discussion of the meta character rules.

  • BTW: The meta characters just match a position in the string, not a part of the string.
  • JK: If that’s the case, I think I’m justifiably confused. Segments suggests it’s a string.
  • MK: We say segment in part to make it clear that it’s not a partitioning. Segments can overlap. This is an attempt to make the previous informal discussion more formal.
  • JK: I just find it more confusing.
  • MK: It’s not easier form a tutorial point of view but I think it’s more formally correct.
  • RD: Would it make sense to add notes to help clarify things?
  • MK: That’s what the “(informally, …)” remarks are for.

Some discussion of bringing them out as note markup.

  • RD: Does this match a standard regular expression library, like PCRE?
  • MK: It’s an attempt to match those conventions, as far as we can discern them.
  • RD: If we could say it’s conformant to or compatible with some other spec…
  • MK: I’m reluctant to do that.
  • JLO: It took me a while, but I think I understand this formulation.

Some more discussion of clarifying the markup to distinguish between single and multi-line modes. There’s room for editorial improvement.

  • WP: I think JK’s point makes it’s point. If JK is confused, then it’s confusing? I agree with BTW, but maybe a few editorial improvements could fix it. There needs to be some sort of gloss.
  • JK: In the terminological layout that’s first presented, we discuss character positions. I’m surprised that’s not referenced anywhere here. Maybe that would fix it.
  • WP: They aren’t partitioning.
  • JK: Substring?
  • MK: We use substring a lot, but it doesn’t have properties to tell you where they start or how long they are.

Some discussion of whether or not the term “segment” implies the absence of overlap.

Proposal: accept this PR.

Accepted.

2.5. PR #2911: 2693 Drop type patterns (and other revisions)

See PR #2911

  • MK: There’s been a fair amount of comentary on this PR. Perhaps we should look at those as well.
  • MK: Patterns that match maps and arrays by types looked too similar to patterns that matched them by content.
    • … There were some odd inconsistencies between type patterns and other patterns
    • … And a lot of duplication of functionality.
    • … This PR tries to provide the same functionality with less duplication and more clarity.
  • MK: The classification of patterns changes.
    • … Mainly to reduce duplication in the spec.
    • … The syntax now splits between traditional patterns, XNodePatterns, and SimplePattern
    • … Simple patterns are to match other kinds of things.
  • MK: Predicate patterns as such are gone.
  • MK: Type patterns are gone. All the important cases are now covered by other syntax.
  • MK: XNodePattern rules are unchanged.

MK introduces SimplePatterns

  • MK: “.” matches anything. We can’t use bare names so atomic(name) matches an atomic. We also have map, record, array, and jnode patterns.
  • MK: Doing instance of is retained from 3.0.
  • MK: Atomic patterns don’t occur very often in the top level, but they appear within other patterns.
  • MK: Sequence pattersn don’t appear at the top level. They’re an ordinary pattern with an occurrence indicator.
  • MK: Record paterns match nominative records.
  • MK: Array patterns match arrays; it looks very similar to the type. That might be confusing.
  • MK: JNode patterns don’t change, except for the predicates being refactored out to a separate part of the spec.
  • MK: The rules for default priority have been reorganized but aren’t supposed to have changed.
  • RD: Is it possible to use a function as a top-level of a pattern?
  • MK: It is for XNode patterns. You can start with the doc function; but it isn’t for new ones. They don’t have hierarchical selection.
  • RD: Do these need to be reserved function names? What if you have a function called array
  • MK: You can only use a very few functions at the top level.
  • JLO: Why is it impossible to generalize those patterns to match both XNodes and atomics and records?
    • … Can we generalize the new patterns to match XNodes as well?
  • MK: I’m not sure what kind of generalization you mean.
  • JLO: One that either deprecates the current patterns or makes it so that we don’t need a separate set of patterns.
  • MK: Generalizing the patterns for element paths is difficult. It would conceptually be possible to do it for JNodes.
    • … We could use the same kind of syntax with / to select JNodes as we do XNodes
    • … But I’m put off by that idea because I think it’s unlikely that users will ever want to write a template that matches both an XNode and a JNode
    • … This makes the distinction visible to both users and the compiler
    • … I considered using a different attribute, but opted against it.

Some discussion of the mixed case, like applying templates to collection().

  • JWL: I can imagine wanting to match a function item in some complicated cases. You can always do it with predicates. If you opened that can, you’d have deal with the fact that array() and map() are also functions.
  • MK: We don’t have all that much machinery for introspection on functions. I’m not sure we could improve on the syntax.
    • … Doesn’t seem obviously useful.
  • JLO: It’s a little confusing that the any pattern can only match XNodes.

MK walks through the whole syntax from the top level.

Some discussion of where you factor in the predicate logic.

Proposal: accept this PR.

Accepted.
