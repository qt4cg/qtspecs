Forwards compatibility of options parameters

I'm having to modify some load-xquery-module tests to specify trusted=true, because the dynamically-loaded module in turn does static imports of further modules. Fortunately the queries still run under 3.1, because in 3.1, processors are required to ignore unknown options.

This makes me question whether it was really wise to make 4.0 processors reject unknown options: it may well be that the option is given a meaning in a future version of the specification.

One way around this would be the XSLT mechanism of forwards compatibility mode: a version N processor executing a query labelled with version N+x should accept and ignore unknown options.

Alternatively, revert this change; make the presence of an unknown option a warning condition rather than an error.

Refactoring of rules for node construction

There is currently a great deal of duplication between the XSLT and XQuery specifications describing basic operations for node construction (specifically, XNode construction). Because it appears in both XSLT and XQuery, it's difficult to reference it normatively from the new fn:update function, which needs to perform many of the same operations. I therefore propose that we define a set of node construction operations in the data model spec, and reference them from XSLT, XQuery, and fn:update where appropriate.

We have already extracted common material relating to XSD validation into one place (section 17.2.4 of F&O) and I'm thinking that the data model spec might be a better home for this.

Candidates for this treatment include

From XSLT: sections 5.7.1 to 5.7.3 on Constructing Simple Content, Constructing Complex Content, Namespace Fixup

From XQuery: much of section 4.12, Node Constructors

It's also possible that this might open the door to creation of a free-standing function library for node construction (something that has always been an ambition of mine) but that's not the primary goal.

There are differences between XSLT and XQuery, for example in the way that duplicate attributes are handled, or in the error codes that are returned, and these will need to be handled by parameterizing the common descriptions in XDM.

function-name() of a partially applied function

There's a special rule for a static partial function application that if all the arguments are placeholders, the function name is retained. That's designed to ensure equivalence between count(?) and count#1.

There's no similar rule for a dynamic partial application. $f(?) should be a no-op, it should return $f unchanged, but it actually drops the function name if there is one.

If we're going to make an exception in one case then we should make it in both.

Problem is exposed by test case fn-function-name-030

[Question: is function-name() actually useful? Would it make more sense if all function items were anonymous?]

Proposal to classify `%fixed` as a non-delimiting terminal symbol

%fixed is currently classified as a "delimiting terminal symbol". Per A.3.2 Terminal Delimitation, this does not call for symbol separators following it, even if the following terminal is a name. So this would be valid:

declare record local:s(%fixeda := 1);

This does not feel right to me. My proposal is to make %fixed a "non-delimiting terminal symbol". This would ask for symbol separators on its right hand side if followed by a name, as in the case above. The preceding token is always a "delimiting terminal symbol" (( or ,), so an extra symbol separator would not become necessary there.

Function assertions in reserved namespaces

3.2.8.7 (Function Types) says: “it is a static error [err:XQST0045] for a user to define a function assertion in a reserved namespace.”

It’s not 100% clear to me what “define” means here. Using an assertion in a function type is not the same as defining one:

local:f#0 instance of %public function() as item()*

An unprefixed assertion name is in the reserved namespace http://www.w3.org/2012/xquery. A note says that this is “in practice … always an error”, but the rule itself doesn’t require it. As a result, test annotation-assertion-20 accepts true or false, not an error.

I would propose to…

  • replace the sentence with: “It is a static error [err:XQST0045] if the name of a function assertion is in a reserved namespace, unless the assertion is defined in a specification, such as %updating in the XQuery Update Facility.”,
  • add function assertions to the description of XQST0045 in the error appendix, and
  • turn the note into a short consequence of the rule: unprefixed names are an error unless they are defined assertions.

%public and %private are annotations, not function assertions, so the exception doesn’t cover them.

Regular expressions: Unicode scripts

Regular expressions support Unicode categories (\p{Lu}) and blocks (\p{IsGreek}), but not scripts. Blocks are a poor substitute: \p{IsGreek} covers U+0370–U+03FF, which includes Coptic letters but not Greek Extended:

matches('ἀ', '\p{IsGreek}')  (: false :)

Scripts are needed, for example, for JSON Schema (IDNA2008 rules, RFC 5892, idn-hostname format).

Proposal:

charProp ::= IsCategory | IsBlock | IsScript
IsScript ::= ("Script=" | "sc=") ScriptName

ScriptName is a script name or short alias from the Unicode Character Database (Greek, Grek), matched case-sensitively:

matches('ἀ', '\p{Script=Greek}')  (: true :)
matches('ἀ', '\p{sc=Grek}')       (: true :)

The implementation effort should be small: most regex engines support it out of the box (JavaScript, Java, ICU, PCRE2, Rust, etc.).

Switch, typeswitch: optional default clause

With switch and typeswitch, default is mandatory. This gets in the way when all possible values are already covered by the case clauses, which is often true for enums:

declare variable $color as enum('red', 'green', 'blue') external;

switch ($color) {
  case 'red' return 1
  case 'green' return 2
  case 'blue' return 3
  default return error()  (: never reached :)
}

Users have to write a default branch that can never be reached. This adds noise, and if the default branch is an error call, it hides missing cases.

Proposal:
* Make the default clause optional in switch and typeswitch expressions.
* If no case matches, raise a new dynamic error.
* Processors may report missing cases statically (for enums, choice types, perhaps other and future cases)

Guarded expressions: missing constructs

The section on guarded expressions says it gives “the complete list of expressions that have guarded subexpressions”. I think some constructs seem to be missing, at least…

  1. Function bodies, for example, let $f := fn() { 1 div 0 } return 1
  2. Lookups, for example, ()?(1 idiv 0)
  3. Predicates: in E[P], P is guarded, but the effective boolean value is computed by the filter expression, not by P. May ()[('a', 'b')] raise FORG0006? I suggest saying that computing the truth value is guarded too.
  4. Quantifiers: Only P in satisfies P is guarded. In some $x in (), $y in 1 idiv 0 satisfies true(), the second binding is not covered. I suggest the same rule as for FLWOR: each binding is guarded by the existence of an item bound in the earlier bindings.

3064 `fn:jvalue`: accept any item

Closes #3064

Issue #3064 created #created-3064

11 Nov at 10:01:30 GMT
Link: https://github.com/qt4cg/qtspecs/issues/3064
`fn:jvalue`: accept any item

fn:jvalue declares its parameter as jnode()?, so any other item raises XPTY0004. This is at odds with how JNodes are handled everywhere else. Examples:

  • Axis steps wrap maps and arrays implicitly: $map/child::* works without an explicit jtree call.
  • fn:jtree was generalized to accept any value (see #2825).
  • Coercion unwraps JNodes silently wherever atomic items, maps or arrays are expected.

As a result, sequences that mix JNodes and plain values arise naturally, e.g. when ? lookups and / steps are combined, and jvalue is the obvious function to normalize them. Currently, this fails:

let $data := { "a": 1, "b": [ 2, 3 ] }
let $items := ($data/a, $data?b?*, $data/b/*)
return $items ! jvalue()

Expected: 1, 2, 3, 2, 3. Instead, XPTY0004 is raised for the plain integers returned by $data?b?*. Users have to write:

$items ! (if (. instance of jnode()) then jvalue() else .)

I think parameter type should be item()?: if $input is not a JNode, it is returned unchanged. The XPTY0004 error for the context value can then be dropped, as only the absent case remains.

fn:jkey could stay as it is: a plain value has no key, and returning the empty sequence would hide errors.

Issue #3062 created #created-3062

Link: https://github.com/qt4cg/qtspecs/issues/3062
`fn:resolve-uri`: non-hierarchical base URIs

According to the rules of fn:resolve-uri, a non-hierarchical base URI is an example of a base that is “not a suitable IRI to use as input to the chosen resolution algorithm”.

However, RFC 3986 5.2 resolves against any absolute base, though. In particular, fragment-only and query-only references are used in practice, for example in JSON Schema, which resolves $ref values such as #/$defs/bar against $id values such as urn:uuid:….

resolve-uri('#s', 'urn:uuid:1234')  (: FORG0002; RFC 3986: urn:uuid:1234#s :)
resolve-uri('?y', 'urn:doi:2345')   (: FORG0002; RFC 3986: urn:doi:2345?y :)

#280 already relaxed the rules for bases with fragment identifiers. I’d suggest going a step further, by dropping the non-hierarchical example from the FORG0002 rule and apply RFC 3986 as written.
