Subtyping of nominative recursive types, wording

Subtyping of Nominative Record Types currently says:

  • For example, if the nominative record type T has the expansion record(A as item()*, B as T?), then the type array(T) is not considered to be equivalent to array(record(A as item()*, B as T?)), despite the fact that the two types have exactly the same instances.

The passage "the two types have exactly the same instances" creates the impression that every instance of the first type is an instance of the second type, and vice versa (in instance of terms). However, it seems to be incorrect.

The array(T) type is a subtype of array(record(A as item()*, B as T?)); thus, every instance of the first type is an instance of the second. However, not every instance of the second type is an instance of the first.

I suppose, the following program would return ( true(), false() ):

declare record T (A as item()*, B as T?);
declare type U as record(A as item()*, B as T?);
let $t as T := map{ "A":1, "B":() }
let $u as U := map{ "A":1, "B":() }
return ( ($t instance of U), ($u instance of T) )

Therefore, $u refers to an item that is an instance of the second type, but not an instance of the first type.

Probably, it is better to replace the phrase "despite the fact that the two types have exactly the same instances" with "but the first type is a subtype of the second".

substring-after-last and substring-before-last

The specifications of these two functions use the phrase

the last occurrence of a sequence of collation units

In the context of ignorable collation units this phrase needs further clarification. Is it the sequence that starts last, or the sequence that ends last?

I suggest a different definition:

substring-after-last(A, B, C)

Consider all pairs of strings (X, Y) such that concat(X, Y) = A. From all such pairs, return the shortest Y that satisfies ends-with(X, B, C)

substring-before-last(A, B, C)

Consider all pairs of strings (X, Y) such that concat(X, Y) = A. From all such pairs, return the longest X that satisfies starts-with(Y, B, C)

Records and simplicity

Our records are making wonderful progress – but in some way they are getting miraculously mysterious. When I recently tried to communicate the current state of the art, I failed miserably to get the details right.

From the feedback I received, I took away that a simplified approach may win in the long term, even if it means discarding some progress, and confronting challenges implementing it (but it has already become quite a challenge to get it right anyway). In short:

1. Structural comparisons

What if a “structural” record type looks exclusively at the (unordered) structure of the data, and if we do not differentiate between maps and records? As a result, the following queries would all return true:

  1. { 'a': 1, 'b': 2 } instance of record(a, b)
  2. { 'a': 1, 'b': 2 } instance of record(b, a)
  3. declare record rec(a, b); { 'a': 1, 'b': 2 } instance of rec
  4. let $x as record(a, b) := { 'a': 1, 'b': 2 } return $x instance of record(a, b)

In all cases, coercion should only be required if instance of yields false: the coercion in example 4 would be a no-op and the order stays as supplied.

2. Naming

I was asked: if we have a “nominative record type”, what will a “genitive” and ”dative” record type” be?…

In a recent and more progressive proposal by Michael, the nominative record type was called “class”. I rejected this first, but the more I think about it, the more I think that distinct terms could be helpful. A compromise would be record class: structural record types could then become plain record types.

The record class declaration could still be declare record… or even declare class, as proposed: it would be consistent: if we decide to push records forward, we will be more and more inspired by OO semantics.

3. Constructors

Again I would like to vote strongly for having record constructors everywhere. It’s the overwhelming default in all languages I looked up, including Java or C#…

record Point(int x, int y) {}
Point p = new Point(1, 2);

…as well as Kotlin, Scala or Python. Python seems to be the only one with an explicit opt-out. If construction must be restricted, a %private record declaration already limits the constructor to the declaring module.

We use records a lot in our code already, and nearly every record (~90%) is instantiated at least once. An additional %constructor would just be boilerplate.

Align trim-space with normalize-space

The normalize-space() function is often used when only leading and trailing whitespace can arise, and it would be nice if trim-space() were a plug-in replacement in that role.

This suggests that it might be convenient for the first argument to default to string(.).

The other difference is that normalize-space(()) returns "" whereas trim-space(()) returns (). I don't feel strongly about that one. The main place it might trip people up is with something like

declare function f ($element) as xs:string {
   trim-space($element/@x)
};

Casting and coercion of recursive types

What are the downsides if these record types are structural (in terms of subtyping and coercion rules)?

The main effect currently is that they can't be recursive (which some of them are).

Originally posted by @michaelhkay in #2908

Subtyping of Nominative Record Types says:

  • Recursive record types are considered to be, in the terminology of the computer science literature, iso-recursive (rather than equi-recursive). This means that a recursive type name is not treated as being equivalent to its expansion (at any depth). For example, if the nominative record type T has the expansion record(A as item()*, B as T?), then the type array(T) is not considered to be equivalent to array(record(A as item()*, B as T?)), despite the fact that the two types have exactly the same instances.

At the same time, according to Casting to a Record Type, an instance of array( record(A as item()*, B as T?) ) can be cast to array(T), and vise versa.

It appears that such a cast, in essential, merely a sort of relabeling. However, for such structural runtime cast, we could need the machinery similar to a structural subtyping algorithm for recursive types.

If that is the situation, why not formally recognize these types as equivalent? Or, otherwise, perhaps casting to recursive nominative types should be restricted?
