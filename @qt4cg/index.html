Effect of "empty greatest" on ordering of NaN

A number of new tests have been committed in test set EmptyOrderDecl demonstrating that XQuery 4.0 produces different sort results from 3.1 in the case of a sequence that includes NaN values. These changes are attributed to a change in the spec consequent on PR #2256.

When I wrote that PR, and when we reviewed it, I don't think we were conscious that we were introducing an incompatible change, and the change is not highlighted in the list of incompatibilities. I'm therefore raising the issue for discussion: do we actually want to make this incompatible change?

To be clear: Sorting the values (), NaN, 1, 4, 7

  • In 3.1 with empty least, the result is (), NaN, 1, 4, 7
  • In 3.1 with empty greatest, the result is 1, 4, 7, NaN, ()
  • In 4.0 with empty least, the result is (), NaN, 1, 4, 7
  • In 4.0 with empty greatest, the result is NaN, 1, 4, 7, ()

Now, I think the 3.1 rules are pretty bizarre (the rationale is probably that SQL has a similar capability if you equate () with SQL's null). I can't imagine that many people use "empty greatest", but if they do, I see no particular reason to impose an incompatible change on them. The bar for an incompatible change should be very high (the fact that we think the new rules are better is not a strong enough reason), and I don't think the justification here is strong enough.

`fn:rename`: renaming nodes

With the just added fn:update function it is tedious to rename nodes: existing entries need to rebuilt. We could simplify with an fn:rename function, which could also be used standalone:

fn:rename(
  $node  as gnode(),
  $name  as xs:anyAtomicType
) as gnode()

Examples:

rename(<item id="1">A</item>, 'entry')
rename(<a b="1"/>/@b, QName('urn:x', 'x:b'))

(: XNodes today :)
update($doc, fn { //item }, fn($item) { element entry { $item/@*, $item/node() } })

(: XNodes with rename :)
update($doc, fn { //item }, rename(?, 'entry'))
update($doc, fn { //@class }, rename(?, 'role'))

(: JNodes today :)
update($json, fn { //customer-id }, fn { { 'customerId': jvalue() } })

(: JNodes with rename :)
update($json, fn { //customer-id }, rename(?, 'customerId'))

2994 File Module: editorial, minor revisions

Some more minor changes (some of them made explicit):

  • file:resolve-path: normalizes all paths (native separators, ./.. removed) and keeps a trailing separator. $base counts as a directory only if it ends with a separator.
  • file:write-binary: $offset now defaults to (). Without it, the file is replaced; with an explicit 0, bytes are overwritten in place.
  • file:base-dir: returns the base URI itself if it points to a directory.
  • file:copy/file:move: missing parent directories are created, and copying or moving into the source's own directory does nothing.
  • Renamed parameters: file:write-text-lines($values) is now $lines; file:children/file:descendants $path is now $dir.

…and editorial trivia.

Update: $replacement argument

As I commented during the review of fn:update, I feel the rules for fn:update handling of the $replacement argument are rather complex and not very intuitive. I propose to experiment with an alternative in which $replacement is always a function that returns a record consisting of an action such as "delete", "replace", "rename" etc, and a value whose interpretation depends on the action.
