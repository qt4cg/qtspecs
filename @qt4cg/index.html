3102 Labeled record types: remaining glitches

Good observations… and I found some more:

  • Constructor functions: parameters without a default value come first, then those with one. This keeps derived record types valid (the geo:place example now follows from the rules).
  • Record extension: inherited fields also count for coercion and casting, not just for the constructor.
  • Fixed fields: a record of a base type can now be coerced or cast to a derived type. Its fixed fields get the values of the target type. A plain map still cannot supply a fixed field.
  • but with: now works for records with fixed fields. Their values are kept, and a fixed field in the second operand is still rejected.
  • Integrity constraints: a violation raises the new dynamic error XPDY0156 instead of XPTY0004, so it can be caught with try/catch. The constraints of base types are checked as well. If the predicate itself raises an error, that error is passed on.
  • Default values of fields are coerced to the field type, as for function parameters.
  • Examples added.
  • Editorial: “static” → “fixed”, typos, R1 → M1, … (makes some observations in #3023 obsolete)

Labeled record types: remaining glitches
  1. When one record type extends another, we say:

The rule that a field with an initializing expression must only be followed by fields with an initializing expression applies to the fields in the declaration only.

How does that affect the constructor function for the derived type? Doesn't it end up with optional parameters followed by mandatory parameters?

  1. §3.4.1 rule 11(b) mentions "static" which should be "fixed"

  2. It seems that if a derived record type contains a fixed field (whether defined as part of the base type or the derived type) then it is not possible either to cast or to coerce the base type to the derived type, even if all the extension fields are optional. This seems to be the case whether or not the fixed field is redefined with a different value in the extension.

  3. No error code is defined for a constructor function when an integrity constraint is violated. For coercion and for casting, the code is given as XPTY0004. But it should be a dynamic error rather than a type error, for the same reason that "zero" cast as xs:integer raises a dynamic error: it's based on data values rather than types, and it's therefore important that it can be caught with a try/catch rather than being detected and rejected statically.

2923 Idempotent coercion

If a value is an instance of a type, coercion to that type now returns it unchanged. This means as a result that function parameter types are now invariant: Functions with more general parameter types no longer match, but can still be coerced.

I was surprised at how much code we would be able to remove from our implementation if we decided to get rid of contravariance. Which no one understood anyway whenever I tried to explain it (could have been my fault, though).

element-to-map() - inferred data types

I'm reviewing where we currently stand with the rules for inferring a data type for elements and attributes in the case where no conversion plan is supplied. There seem to have been a number of changes, and I'm not sure the current spec is coherent.

The expected results of test cases are also inconsistent (which is what led me here). Tests -210, -221, -225, -274 and others expect to output numeric values as strings, while -589 outputs them as numbers.

§14.6.9 seems to suggest that elements and attributes are treated differently:

If the conversion plan has no entry for an untyped element (including the case where no plan is supplied), the type is inferred from the string value of the individual element instance by applying the rules in [14.6.3 Inferring a data type] and the selected type is treated as the prescribed type. No such inference takes place for attributes: if the plan has no entry for an attribute, no type is prescribed.

I can't see any possible logic for treating elements and attributes differently; and in any case the spec goes on to say:

In the case of untyped elements and attributes, the value is output as an instance of a string, numeric, or boolean type, according to this prescription:

which makes little sense if there is no prescription.

The spec goes on to say:

If the prescribed type is boolean and the value is castable as xs:boolean, then it is output as the xs:boolean value true or false.

but I thought we had decided that numeric took precedence: in the absence of any conversion plan, <a>1</a> should be output as {'a': 1} not as {'a': true}. In fact, §14.6.9, having normatively referenced §14.6.3, then seems to contradict it by applying a different set of rules. (§14.6.3 prefers numeric to boolean in this case).

`MethodCall`: placeholder restriction is stated in prose but reported as `XPST0003`

The grammar for MethodCall allows argument placeholders, because it reuses PositionalArgumentList:

MethodCall             ::= PostfixExpr "=?>" NCName PositionalArgumentList
PositionalArgumentList ::= "(" PositionalArguments? ")"
PositionalArguments    ::= (Argument ++ ",")
Argument               ::= ExprSingle | ArgumentPlaceholder

The prose then forbids them:

The argument list in a method call must not include an argument placeholder; that is, the call must not be a partial function application [err:XPST0003].

But $x =?> f(?) is a valid instance of the grammar, and XPST0003 is only defined for grammar violations. This is the same kind of problem as in #3038. The test case method-920 covers this case.

Proposal: exclude placeholders in the grammar and delete the sentence:

MethodCall         ::= PostfixExpr "=?>" NCName MethodArgumentList
MethodArgumentList ::= "(" (ExprSingle ** ",") ")"

Alternatively, XPST0017 could be extended to cover this case, or even a new error code could be introduced.

Function assertions: match annotations

Function assertions and annotations look identical but are unrelated. The following query reads like “is f private?”, but the assertion is either rejected or ignored:

declare %private function f() {};
f#0 instance of %private function(*)

Proposal: A function assertion %N matches a function item if the item has an annotation N (with the same values, if arguments are given). Assertions defined in a specification, such as %updating` in the XQuery Update Facility, keep their own semantics. XQST0045 is no longer raised for function assertions.

Options with default `()` should have optional type

In most functions, an option with default () has an optional type (xs:string?, xs:QName*, …): match in fn:collection, encoding in fn:unparsed-text, etc. Examples:

  • fn:collation: version and strength default to (), but their types (xs:string, enum(…)) don’t allow it.
  • fn:collection: form is xs:string, whereas fn:uri-collection declares the same option as xs:string?.
  • fn:parse-html: encoding is xs:string without default, fn:unparsed-text and fn:unparsed-text-lines use xs:string?.
