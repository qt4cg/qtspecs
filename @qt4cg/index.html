Regex formalism does not account for group nesting

The formalism for evaluating regular expressions gives the impression (and has the intent) that the results of all regex functions can be obtained from knowledge of matching segments: in effect, that the output of matches(), tokenize(), replace() etc can all be derived from the result of fn:matching-segments. However, this is not the case. Consider the two expressions

matching-segments("a", "(a(b?))")

These produce the same result, namely

Link: https://github.com/qt4cg/qtspecs/issues/3034
Constructor functions for records

I believe that there are many cases where a labeled record type is useful, but it is inappropriate to provide the default constructor function for the record type.

This is exemplified by the built-in labeled record types. Most of these are defined as the return type of a function, and the appropriate way to create an instance of the record type is by calling that function.

Consider also the worked example set:atomic-set. The library module defining this type defines a custom constructor function, called for example as set:of(("a", "b", "c")). The default constructor function, by contrast, takes as its input a map; this exposes internal implementation details, and although we can't prevent direct access to the internal structure, we really don't want to encourage people to use it. We could use the proposed integrity constraint mechanism to ensure that the supplied map has the correct form, but this might impose significant performance overheads.

Because an implicit constructor function is created with the name of the record type, it's impossible to create a user-defined function with that name that performs a more nuanced construction, for example with extra validation and creation of internal data fields.

So I think we should certainly provide the opportunity to disable implicit creation of a constructor function, and I would go further and say, from my experience, that this should be the default.

We also create constructor functions for a simple record type declared in a "declare type" declaration. In this case the constructor function offers very little convenience over direct use of the map constructor, and in my view it is likely to be confused with the different semantics of a constructor function for labeled record types. I therefore propose that constructor functions should not be available for simple record types.

Evaluation of function parameter defaults

Test case function-decl-40-060 does

<test-case name="function-decl-40-060" covers-40="PR2941">
      <description>Default values of function parameters.</description>
      <created by="Christian Gruen" on="2026-10-10"/>
      <dependency type="spec" value="XQ40+"/>
      <test><![CDATA[
         declare function local:f($x := <a/>) { $x };
         local:f() is local:f()
      ]]></test>
      <result>
         <assert-true/>
      </result>
   </test-case>

This is assuming that the expression for computing the default value is only computed once. The justification for this assumption in the spec is very weak; what we say is:

A default value that does not depend on the focus is fixed: every function call that defaults the relevant argument supplies the same value. A default value that depends on the focus will typically supply a different value for every such call; it may also lead to a type error if the context value is absent or has the wrong type.

But the question of whether the default value "depends on the focus" is not clearly defined by anything in the spec. For example, consider the expression if (position() gt 0) then <a/> else <b/>. We don't say whether we're talking about a static dependency or a dynamic dependency. There are other edge cases where determining statically whether an expression has a dependency on the focus is not straightforward: consider a function call (perhaps a recursive function call) that defaults some arguments.

In XSLT there is the additional complication that the dynamic context includes other things (beyond the focus) that can vary from one call to another, such as the value of current-group(). I think we should explicitly ban such things from default value expressions. XSLT says in a note " It is not possible for a user-defined function to reference other aspects of the static or dynamic context of the caller, such as the static base URI or the default collation." but it's not clear whether there is any normative rule to justify this claim.

I don't think this interpretation of every function call that defaults the relevant argument supplies the same value was intended, and I suggest changing the spec (and this test case) to clarify it. We should leave it implementation defined whether the expression is evaluated on every call, or whether the result of an evaluation is reused.

XSLT says, in §9.2.2:

This specification does not dictate whether and when the default value of a parameter is evaluated. For example, if the default is specified as <xsl:param name="p"></xsl:param>, then it is not specified whether a distinct foo element node will be created on each invocation of the template, or whether the same foo element node will be used for each invocation.

Method invocation syntax: might `$rectangle/size()` work?

I'm wondering if we could make $rectangle/size() work to invoke a method, as replacement for $rectangle =?> size()? If we can, it's a lot more intuitive, since people are used to writing things like $element/name().

Under the current rules, if $rectangle is a record (or a map), then $rectangle/E is valid syntax, but it only has defined semantics if E is either a (a) navigational expression, or (b) an expression that does not depend on the context. So $rectangle/size() is legal, but unlikely to be useful. We would essentially define a third category for E: if it takes the syntactic form of a static function call (or more precisely, an NCName followed by a PositionalArgumentList), then it is interpreted as a method invocation.

Quotes around literal map keys

In many contexts we allow the quotes around an NCName-valued map key to be omitted: notably in a lookup expression $rectangle?x, in a path expression $rectangle/x, and in a constructor function rectangle(x := 3).

This makes it jarring that the quotes are needed in a map constructor {'x': 3}. Omitting the quotes is a common source of error (given that they aren't needed in Javascript), and it can be difficult to debug because the construct is syntactically valid.

We could special-case this, as we have done in the other cases listed above. The syntax is

MapConstructorEntry ::= ExprSingle (":"  ExprSingle)?

We could say that in a MapConstructorEntry that starts with an NCName followed by ":", the NCName is interpreted as a string literal rather than as an element name. For backwards compatibility the rule would only apply if the map keyword is omitted from the map constructor.

Using an element name in this syntactic context is vanishingly unlikely, and if required, the effect can be achieved by prefixing it with child::.

Another option would be to allow the alternative syntax

MapConstructorEntry ::= NCName ":="  ExprSingle

aligning map constructors with calls on record constructor functions:

point(x:=5, y:=7) but with {y:=9}

Change %static keyword

The keyword %static, applied to fields in a labeled record type, is misleading, because such fields are most often used to hold methods that have access to the record instance, unlike static methods in OO languages.

The keyword %final would be a better reflection of the semantics.
