Link: https://github.com/qt4cg/qtspecs/issues/3095
`MethodCall`: placeholder restriction is stated in prose but reported as `XPST0003`

The grammar for MethodCall allows argument placeholders, because it reuses PositionalArgumentList:

MethodCall             ::= PostfixExpr "=?>" NCName PositionalArgumentList
PositionalArgumentList ::= "(" PositionalArguments? ")"
PositionalArguments    ::= (Argument ++ ",")
Argument               ::= ExprSingle | ArgumentPlaceholder

The prose then forbids them:

The argument list in a method call must not include an argument placeholder; that is, the call must not be a partial function application [err:XPST0003].

But $x =?> f(?) is a valid instance of the grammar, and XPST0003 is only defined for grammar violations. This is the same kind of problem as in #3038. The test case method-920 covers this case.

Proposal: exclude placeholders in the grammar and delete the sentence:

MethodCall         ::= PostfixExpr "=?>" NCName MethodArgumentList
MethodArgumentList ::= "(" (ExprSingle ** ",") ")"

Alternatively, XPST0017 could be extended to cover this case, or even a new error code could be introduced.

Function assertions: match annotations

Function assertions and annotations look identical but are unrelated. The following query reads like “is f private?”, but the assertion is either rejected or ignored:

declare %private function f() {};
f#0 instance of %private function(*)

Proposal: A function assertion %N matches a function item if the item has an annotation N (with the same values, if arguments are given). Assertions defined in a specification, such as %updating` in the XQuery Update Facility, keep their own semantics. XQST0045 is no longer raised for function assertions.

Options with default `()` should have optional type

In most functions, an option with default () has an optional type (xs:string?, xs:QName*, …): match in fn:collection, encoding in fn:unparsed-text, etc. Examples:

  • fn:collation: version and strength default to (), but their types (xs:string, enum(…)) don’t allow it.
  • fn:collection: form is xs:string, whereas fn:uri-collection declares the same option as xs:string?.
  • fn:parse-html: encoding is xs:string without default, fn:unparsed-text and fn:unparsed-text-lines use xs:string?.

2846 file:write, file:append: defaults, notes

I started off with the intent to make the file write functions more liberal, and I ended up making them adhere closer to fn:serialize… I believe that we should define fn:serialize more rigorously, instead of introducing too many rules that target file output, so that in most cases…

$data -> file:write($file, ., $options)
$data -> serialize(., $options) -> file:write-text($file, .)

…will remain equivalent (except for byte-level issues, such as encoding and BOM treatment).

Forwards compatibility of options parameters

I'm having to modify some load-xquery-module tests to specify trusted=true, because the dynamically-loaded module in turn does static imports of further modules. Fortunately the queries still run under 3.1, because in 3.1, processors are required to ignore unknown options.

This makes me question whether it was really wise to make 4.0 processors reject unknown options: it may well be that the option is given a meaning in a future version of the specification.

One way around this would be the XSLT mechanism of forwards compatibility mode: a version N processor executing a query labelled with version N+x should accept and ignore unknown options.

Alternatively, revert this change; make the presence of an unknown option a warning condition rather than an error.
