Edge cases with CSV serialization

I think there are a few edge cases that aren't covered by the spec, for example what heppens if a string after Unicode normalization contains the quote or separator character?

I would suggest making it simpler, in the interests of being easier to understand and easier to implement, while not affecting any practical use cases. Put each string through the following steps, in order, each applying to the output of the previous step.

  1. Apply character mapping if requested.
  2. Apply unicode normalization if requested.
  3. Normalize line endings.
  4. Apply quoting to strings that (now) contain special characters.

Note: character mapping was originally designed with the primary use case of manually generating XML markup, which is why the XML output method doesn't interfere with strings generated using character mapping. That justification doesn't apply here.

Add a function that converts an absolute URI into a relative URI with respect to a given base

I suggest a new function in the section for "Parsing and building URI". It takes two absolute URIs, and converts one of them to a relative URI with respect to the other URI, if possible.

A usecase could be: Add a reference to an image to a document. The absolute path to the image points to a directory within my document file structure, but i prefer relative references within my document. The new function is related to fn:resolve-uri.

The function takes two URIs called u1 and u2 as input. The result shall be empty, if

  • the two URIs differ in scheme and / or host, or
  • any of the URIs contain a query and/or fragment part, or
  • any of the URIs is not absolute, or
  • there is no common prefix in both partportions

Otherwise, the result shall be a relative URI r, so that resolve-uri(r, u1) eq u2 holds.

Examples:

  • relative-uri('file:/a/b/c/d','file:/a/b/c/') gives d
  • relative-uri(' http://example.com/dir1/dir3/other.html', 'http://example.com/dir1/dir2/page.html') gives ../dir3/other.html
  • relative-uri(' http://example.com/dir1/dir3/other.html', 'https://example.com/dir1/dir2/page.html') gives the empty sequence because of different schemes

Greetings, Frank Steimke

2853 Default values of function parameters

Fix #2853

This resolves the issue as follows:

  • In both XSLT and XQuery, the expression defining the default value of a function parameter (for a user-defined function) is evaluated in the same way as the initializing expression of a global variable. We don't constrain the expression, but it has no access to the static or dynamic context of the function caller, and it defines a fixed default that applies to all calls on that function.
  • However, as a special case there is provision to define that the context item/value of the caller is used as the default. In XQuery this is done by defining the default using the custom syntax $node as node() := context value. In XSLT we use select="current()".

Default values of function parameters

XSLT and XQuery have slightly different rules for how context dependencies are handled in expressions beng used to define the default values of function parameters. For example, if the default is given as "static-base-uri()", then I don't think XQuery makes it clear whether this is the static base URI of the function definition, or the static base URI of the caller.

Variable references within the default value expression are particularly problematic and I think we should make it explicit that they are not allowed. We could allow references to global variables but even that is complicated because of visibility issues if the variable is not visible to the caller. XSLT on the current rules gets into a complete mess if the default value is given as "$var" when the static context of the function definition and the dynamic context of the caller include different variables both called "$var".

It's fairly obvious, I think, that namespaces should be resolved using the static context of the function definition: but I'm not sure that XQuery says so explicitly. Resolving function references such as fn:true#0 should also use the static context of the function definition. But what about a call to function-lookup()?

xs:integer vs. restricted subtypes

4.0 added relabeling, so xs:positiveInteger can now be used as parameter or return type. Seven places already do that: fn:char, fn:partial-apply, fn:replicate, fn:unix-dateTime, the select-columns option, location-record, parsed-csv-structure-record?get.

I would definitely prefer to maintain the pre 4.0 tradition to use xs:integer:

  • It will produce different errors for values with a [min:max] range (for example fn:char, fn:parse-csv/select-columns, fn:radix).
  • It is not obvious at all that xs:positiveInteger excludes 0, or how that even differs from xs:nonNegativeInteger.
  • It will thus result in confusing error messages (“xs:positiveInteger expected” instead of custom “out of bounds” errors).
  • We cannot adjust most existing functions, so this will result in inconsistent language behavior.

From the implementation perspective, relabeling may require additional (un)boxing, or conversion of values that are stored in a compact representation. Optimizations that test for exact xs:integer items/sequences stop matching.

In my opinion, relabeling remains useful where users declare their own narrow types and can judge the cost. The built-in library is the wrong place to spend it.

If we decide that we want to have stricter typing, we should be consistent and introduce it everywhere, for example…

  • matching-segment-record?position; captured-group-record?position, ?nr; uri-structure-record?port; arity keys of load-xquery-module-record?functions; $groups keys of fn:replace
  • return types: fn:index-where, fn:jposition, and possibly fn:count, fn:string-length, fn:position, fn:last, fn:index-of, …
  • $pos callback parameters (fn:filter, etc.)
