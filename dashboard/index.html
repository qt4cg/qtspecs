PR #3103: 3102 Labeled record types: remaining glitches

Pull request #3103 by ChristianGruen.

Good observations… and I found some more: * Constructor functions: parameters without a default value come first, then those with one. This keeps derived record types valid (the `geo:place` example now follows from the rules). * Record extension: inherited fields also count for coercion and casting, not just for the constructor. * Fixed fields: a record of a base type can now be coerced or cast to a derived type. Its fixed fields get the values of the target type. A plain map still cannot supply a fixed field. * `but with`: now works for records with fixed fields. Their values are kept, and a fixed field in the second operand is still rejected. * Integrity constraints: a violation raises the new dynamic error XPDY0156 instead of XPTY0004, so it can be caught with try/catch. The constraints of base types are checked as well. If the predicate itself raises an error, that error is passed on. * Default values of fields are coerced to the field type, as for function parameters. * Examples added. * Editorial: “static” → “fixed”, typos, `R1` → `M1`, … (makes some observations in #3023 obsolete) Closes #3102 Tests: https://github.com/qt4cg/qt4tests/pull/529

PR #3100: 2923 Idempotent coercion

Pull request #3100 by ChristianGruen.

If a value is an instance of a type, coercion to that type now returns it unchanged. This means as a result that function parameter types are now *invariant*: Functions with more general parameter types no longer match, but can still be coerced. I was surprised at how much code we would be able to remove from our implementation if we decided to get rid of contravariance. Which no one understood anyway whenever I tried to explain it (could have been my fault, though). Closes #2923 Tests: https://github.com/qt4cg/qt4tests/pull/527
